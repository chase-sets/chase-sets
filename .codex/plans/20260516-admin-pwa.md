## Owning Contexts

- Primary owner: `deployables/admin-web` as a thin composition root for host-level browser capabilities.
- Contributing route contexts remain unchanged:
  - Auth owns sign-in, sign-out, session lifecycle, and actor resolution.
  - Identity owns user, account, membership, invitation, API key, consent, and admin identity-management surfaces.
  - Catalog owns catalog authoring and catalog admin surfaces.
  - Commercial Terms owns fee policy and commercial-agreement admin surfaces.
  - Experience owns platform feedback and internal feedback review surfaces.
  - Public Presence owns waitlist behavior and internal waitlist review surfaces.
- No bounded context takes ownership of PWA installability because the manifest, service worker route, and root metadata are deployable host infrastructure.

## Resolved Decisions

- Decision: Implement PWA support inside `deployables/admin-web`.
  - Why it matters: bounded contexts own behavior, UI, and tests for their routes; deployables own only host composition and runtime bootstrap.
  - Repo evidence: `docs/architecture/bounded-context-structure.md` says deployables remain thin roots; `deployables/marketplace` already owns manifest, service-worker route, and registration code for its host.
  - Consequence of choosing differently: putting service-worker or manifest behavior into a bounded context would make one context own a browser capability that affects all admin sections.

- Decision: Use a conservative admin service worker.
  - Why it matters: admin pages are authenticated operational workflows and can expose sensitive user, catalog, commercial terms, waitlist, and feedback data.
  - Repo evidence: Auth owns browser sessions and session cookies; admin context APIs require auth; marketplace service worker already excludes credentialed requests and transactional paths.
  - Chosen behavior: register only in production builds; cache static assets and icons; use an offline fallback route for document navigations only when the browser is offline; do not cache credentialed requests, API responses, or admin document responses.
  - Consequence of choosing differently: document or API caching could show stale admin data after sign-out, actor switch, permission changes, or projection replay.

- Decision: Add an admin-specific manifest rather than reusing marketplace copy.
  - Why it matters: the installed app label and description should match the internal operational surface.
  - Repo evidence: marketplace manifest is deployable-specific and references shopping/productivity categories and marketplace localization keys.
  - Consequence of choosing differently: install prompts and OS app surfaces would blur internal admin workflows with the public marketplace.

- Decision: Reuse the existing Chase Sets icon asset style where practical.
  - Why it matters: PWA installability requires icon assets, and brand consistency is a host-level concern.
  - Repo evidence: marketplace already keeps install icons under `deployables/marketplace/public/icons`; admin-web currently has favicon routes but no `public` icon directory.
  - Consequence of choosing differently: generating a separate icon system for admin would add visual and maintenance entropy without improving the workflow.
