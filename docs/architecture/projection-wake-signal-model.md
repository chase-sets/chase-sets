# Projection Wake Signal Model

Projection wakes are acceleration hints over durable state, not correctness state. The durable event store, projection checkpoints, and read-after-write polling remain the correctness floor; the wake/signal runtime narrows the time between a committed source event and the worker that should reconcile a target projection.

**Relay.** Diagram in prose: source databases emit event-store wake notifications after commit; one worker-owned relay session listens to the enabled source channels, catches up from durable event rows, maps each source wake through the interest index, and writes projection wake intents into the control-plane store. The relay is event-driven fan-out from notifications. It should live in worker-host wiring, because it owns listener connections, relay leases, source cursors, notification rejection handling, and catch-up after reconnects.

**Scheduler.** Diagram in prose: the control-plane store holds queued wake intents by lane; worker scheduler runners periodically claim due intents, run the matching projection group under the existing projection lease, record checkpoint readiness, then complete, retry, or requeue the intent. The scheduler is periodic reconciliation. It should live in worker-host wiring, because it owns lane concurrency, retry cadence, projection lease use, and cleanup of expired work-signal rows.

**Store.** Diagram in prose: API, relay, reconciliation, and operator paths all converge on the durable work-signal store in the control database; wake intents say which source position a target projection should reach, checkpoint readiness rows say which source positions are already visible, and waiter rows are optional durable hints for future readiness-notification paths. The store is the durable queue. Consumers that need wake-before-wait behavior should use `@chase-sets/platform-runtime/work-signal-store`, with `readConsistencyGateway` enabled on `createPostgresWorkSignalStore` when the API read-consistency middleware should enqueue hot-lane `api-wait` intents before falling back to durable polling.

**Registry.** Diagram in prose: each source context has one rollout entry with phase, wave, owner, affected projections, route dependencies, load estimates, production gate evidence, and enablement switches for event-store wake emission and relay fan-out. The registry is configuration. Source-context service factories should derive write-side wake notification settings from `createEventStoreWakeNotificationConfigForSourceContext`, and workers should derive enabled relay sources from `listSourceContextWakeRelayConfigs`.

**Interest Index.** Diagram in prose: projection group subscriptions and read-after-write route dependencies compile into a versioned source-to-projection map; source context, event type, and stream category lookups produce the minimal wake-intent targets while preserving the safe over-wake invariant. The interest index is cardinality. Workers build it once for relay fan-out and report its summary to operator surfaces; API route authors usually declare dependencies in their bounded-context route inventory instead of calling index helpers directly.

Consumer guidance: most application and context code wants store + registry. The store gives durable queue/readiness behavior without listener ownership, and the registry gives canonical source-context wake configuration. Relay and scheduler are worker-host wiring, not general-purpose application dependencies. Do not merge relay and scheduler: relay turns source notifications into durable intents, while scheduler reconciles durable intents into projection checkpoint progress.
